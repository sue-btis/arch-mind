How should arch-mind be built?

By the end, the author can choose how arch-mind is built (views, capture, review, taxonomy) and defend why.

Source of every claim: docs/discovery/findings.md and the two probes in docs/discovery/spikes/. Each claim carries one label: Confirmed a source or a measurement says it; Hypothesis inferred or not checked yet; Ask only you know it; Problem the evidence is broken or missing.

Before you start

arch-mind is a personal tool you plan to build to learn software architecture. Concepts come up while you work with Claude Code, the AI coding assistant you use in your projects. arch-mind should capture each concept from that session, show it in small views next to related concepts, and bring it back for review as questions. "You" in this book is its author and only user.

You agreed on these criteria before seeing any option:

CriterionType
1. Helps remember: weeks later you can explain the concept from memorymust
2. Own, readable views: each view reads at a glance and has your own designmust
3. Frictionless capture: saved from Claude Code, same session, under a minutemust
4. Relations with a source: every relation says where it comes from (docs, standard, or your project)must
5. Learn by building itnice to have
6. A sixth must you selected without writing itmust, text pending

A kill criterion was also fixed: if an existing tool already meets the four musts, adopt it instead of building. Concepts are sorted by layer, the part of a system where they live: client (the browser or app), network (what travels between machines), server, and data. A probe is a small throwaway program built only to measure something; this discovery built two. A challenger, a separate AI reviewer with no prior context, then checked every claim against its sources.

Part I · The problem

1Why do architecture answers get forgotten?

Short answer Understanding an answer while you read it is not the same as remembering it. Two activities make knowledge stick: building the map of relations yourself, and pulling the answer back from memory later. Looking at a finished map helps, but less.

Case

In a web project, Claude asked you how to serve the app locally for test TST-032, an automated check of the site in Safari's engine and in Lighthouse (Google's tool that audits a page's quality). The question looked like one problem. It was a chain of thirteen concepts:

  1. Your session cookie uses the __Host- prefix. A cookie with that prefix must also carry the Secure flag, which means "only send me over a safe connection". Confirmed (cookie draft standard, §4.1.3.2)
  2. Each browser decides what counts as a safe connection. In your project, WebKit (Safari's engine) did not treat http://localhost as safe and dropped the cookie. Hypothesis (seen in your project, not checked against WebKit's docs)
  3. In production mode, next start (the command that runs a Next.js site as in production) sends a security header, the CSP (content security policy), with the rule upgrade-insecure-requests. That rule tells the browser to switch every http request to https. Confirmed for what the rule does (W3C spec, §3.1)
  4. Over plain http, that switch breaks the Lighthouse run. Hypothesis (seen in your project)

One question touched 13 concepts and 15 relations (counted in the view probe). You understood it when you read it. Would you be able to explain step 2 two weeks later?

Mechanism

Research compares three ways of studying. The numbers are effect sizes: how far a group's average score moved compared with a group that studied another way.

Way of studyingEffectWhat it meansEvidence
You build the map of relations0.72The middle learner moves to about percentile 76Confirmed via a summary
You study a map someone else made0.43The middle learner moves to about percentile 67Confirmed via a summary
You recall answers from memory—Beat building concept maps, even on questions that need reasoningConfirmed direction (Karpicke & Blunt 2011)
Percentiles from the normal curve: an effect of 0.72 moves the middle (50th) learner to the 76th percentile, because Φ(0.72) ≈ 0.76; for 0.43, Φ(0.43) ≈ 0.67.

The first two numbers come from one meta-analysis (Schroeder et al. 2018, 142 effect sizes). Each is measured against its own comparison group, so they are not a head-to-head race. They still point the same way: what you produce sticks better than what you receive.

Why it matters

A beautiful map that you only look at is the weakest of the three. arch-mind has to make you build relations and pull answers back from memory. Pretty views alone do not meet your first must, "helps remember".

What we don't know

Problem No study tests the case arch-mind creates: an AI proposes the relations and you accept them. Hypothesis Spacing reviews over days helps memory; the spacing papers were not fetched.

If building and recalling is what works, does any existing tool already do it?

Part II · The options

2Do I need to build anything?

Short answer No surveyed tool meets your four musts at once. You tried Obsidian and ruled it out. The leading option is a hybrid: each concept lives in a Markdown file, and your own app reads those files to draw views and run reviews.

Case

The closest tool was Obsidian with three community plugins: Breadcrumbs for typed relations, Juggl for small styled graphs, and Spaced Repetition for reviews. Confirmed each plugin does its own part. Hypothesis A relation cannot carry its own source, and a view cannot be filtered by layer. You reviewed it yourself and said it does not reach what you want. Twelve other tools were surveyed (Anki, Logseq, RemNote, Heptabase, Tana, Kumu, TheBrain and more). None covered capture from Claude Code, sourced relations, focused views and scheduled recall together. Hypothesis, moderate confidence: several product pages could not be fetched.

Mechanism

In the hybrid, the files are the single source of truth. A Markdown file is plain text that any editor, Git or Obsidian can open. The top of each file, the frontmatter, holds the structured part: layer, relations with their sources, and recall questions. A capture skill writes the files; the app reads them and draws. The probe in chapter 5 wrote this file:

---
id: "secure-attr"
title: "Secure cookie attribute"
layer: "client"
relations:
  - { type: "needs", to: "secure-context", source: "draft-ietf-httpbis-rfc6265bis" }
recall:
  - "Why did WebKit drop the session cookie over http://*.localhost?"
---
A cookie with Secure is only sent over secure transport.

Why it matters

The kill criterion did not fire, so building is justified. The hybrid matches what you said: Markdown gives compatibility with modern tools. It also lowers the risk of building: your data never depends on the app.

What we don't know

Hypothesis The review history (dates and answers) is the one thing the app must write. Where it lives, inside each concept file or in a separate file, is untested. Writing review dates into concept files on every review would add noise to Git history.

If you build it, who should create each relation: Claude, or you?

3Who should draw the relations?

Short answer The evidence leans toward you building the relations, with caveats: the numbers are not a head-to-head test, and nobody has studied accepting relations an AI proposes. A middle path: Claude proposes candidates with their sources, and you choose and explain each one in your own words.

Case

You capture "Secure cookie attribute" after TST-032. Claude proposes three candidate relations, each with a source. You keep one, "Secure cookie is sent only over a secure context", and write one sentence: "WebKit did not count localhost as secure, so the cookie never left the browser." Claude turns your sentence into a recall question: "Why did WebKit drop the session cookie over http://localhost?"

Mechanism

Chapter 1 showed two effects: building a map (0.72) beats studying one (0.43). Choosing among proposals sits between those two. Writing the reason in your own words, called explain-back, moves it closer to building. Hypothesis This option was added by the challenger and not researched.

The two ideas below fit together: explain-back is for each relation, SEE-I for the concept as a whole.

You proposed a structured version for the concept itself: SEE-I. You State the concept in one sentence, Elaborate it in other words, give an Example, and Illustrate it with an analogy or picture. For the Secure cookie: State "a Secure cookie only travels over a connection the browser trusts"; Elaborate "the browser, not the server, decides what counts as trusted"; Example "WebKit dropped it over http://localhost in TST-032"; Illustrate "like a courier who only delivers to a building with a guard at the door". Each part can become one recall question. Hypothesis The method comes from Paul and Elder's critical-thinking work (not fetched); you report it works for you.

Why it matters

This sets a trade-off between two of your musts. More work from you per capture helps memory (first must). Less work keeps capture under a minute (third must).

What we don't know

Problem No study measures choosing among AI proposals. Ask Is one sentence per relation acceptable effort for you?

Once you have chosen and explained the relations, how should they be drawn on screen?

4How should a view be drawn?

Short answer You picked two of the four probe layouts: columns by layer (A) and the matrix (D). They seem to do different jobs: A for following a chain, D for checking every relation at once. A does not fit one screen yet, and "reads at a glance" still needs a definition.

Case

The probe drew the same 13 concepts and 15 relations from chapter 1 in four ways.

LayoutCrossing pairsSizeWhat you see
A · Columns by layer01,954 × 348 pxClient, network, server side by side; needs sideways scrolling
B · Automatic layers01,474 × 318 pxLayers mixed; only color shows them, so position tells you nothing about the layer
C · Hand-placed lanes5980 × 430 pxFits a screen; straight lines, so not comparable
D · Matrix0, by construction, not measured—Every pair visible; following a chain means jumping rows
A crossing pair is two relations whose lines cross. It is a rough proxy: it ignores bends, lines passing under boxes, and labels that collide.

Mechanism

A layered layout sorts concepts into ranks so arrows mostly point one way, then reorders each rank to reduce crossings. Layout A adds a partition per layer, which forces client concepts left of network concepts and network left of server. That ordering is why it grows wide. An adjacency matrix lists concepts as both rows and columns and writes each relation in the cell where they meet, so nothing can cross.

Why it matters

Your second must, own and readable views, is decided here. The rendering engine becomes a design decision. elkjs, the engine behind A, is maintained (version 0.12.1, Oct 2026). Hypothesis The probe used the older 0.9.3; the newer version may place nodes differently, so the sizes above could change.

What we don't know

Ask What does "at a glance" mean for you: no sideways scrolling at 1,366 px wide? Sources readable without hovering? Hypothesis Two untested options could fix A's width: stacking layers as horizontal rows, with an automatic placer (a "solver") that keeps each concept inside its row and only chooses the order and the arrow paths, or a focus view that starts at one concept and shows its neighbors.

Views draw what is stored. How does a concept get stored from a Claude Code session?

5How do capture skills reach the store?

Short answer There are six paths. The probe tested the leading one, a plugin with a small local MCP server: it rejected a relation without a source and wrote a readable Markdown file. Two things are still unmeasured: whether Claude Code asks your permission before saving, and how long a full capture takes.

Case

The probe server received the "Secure cookie attribute" concept and saved it as secure-attr.md. When given a relation with no source, it refused with "relation 0 needs type, to and source". When given the same concept twice, it refused the duplicate. Confirmed by node check.mjs on 30 Oct 2026. That script talked to the server directly, the way Claude Code would, but without Claude Code in the middle; the real flow inside a session is not tested yet.

Mechanism

MCP (Model Context Protocol) is how Claude Code talks to outside tools. In the stdio form, Claude Code starts the server as a child program and they talk through its text input and output. No network port opens, so a web page in your browser cannot reach it. A plugin can bundle the capture skill and this server together. Confirmed (Claude Code plugin docs).

PathValidates dataWorks with app closedMain risk
Skill edits files directlyNoYesAnything can be written
Local web API of the appYesNoWeb pages can attack local servers unless guarded
Plugin + stdio MCP serverYesYesRuns with your user's rights: a bug could touch any of your files
Inbox you accept inside the appAt importYesCapture is not final until you open the app
Command-line tool called by the skillYesYesUntested
Files + a Claude Code hook that checks themAfter writingYesUntested

Two paths need a word. In the inbox, the skill only appends the concept to a waiting list, and nothing becomes final until you open the app and accept it, so capture costs a second step. A hook is a script Claude Code runs automatically after each file edit; it could check the file, but only after it was written. The plugin path leads because it is the only one that checks the data before saving, works with the app closed, and opens no network port; the command-line and hook paths are untested.

Why it matters

Your third and fourth musts meet here. Capture without friction needs the path to work with the app closed. Relations with a source need someone to refuse a relation without one.

What we don't know

Ask Run the plugin once in a normal session to see whether it asks permission; the automated check could not run because the background Claude Code process was not signed in. Problem The server only checks that the source is not empty; "x" would pass, and it does not check that the related concept exists.

Saved concepts come back as recall questions. When should they come back?

6When should recall questions come back?

Short answer A scheduler decides when each question returns. The simplest, Leitner boxes, takes a few lines of code. FSRS, the most studied, predicts forgetting better than a baseline that gives every question the same chance, on about 350 million reviews from the open srs-benchmark, but no comparison against the older SM-2 method was found. With 50–300 concepts, simple is enough to start.

Case

Leitner boxes: box 1 waits 1 day, box 2 waits 3, box 3 waits 7, box 4 waits 16, box 5 waits 35. A right answer moves the question up one box and waits that box's gap; a wrong answer sends it back to box 1. For "Why did WebKit drop the session cookie?":

DayBoxYour answerNext review
01capturedday 1
11right → box 2box 2 waits 3 days → day 4
42right → box 3box 3 waits 7 days → day 11
113wrong → box 1box 1 waits 1 day → day 12
The gaps 1, 3, 7, 16, 35 are an example, not a researched value.

Mechanism

A scheduler estimates when you are about to forget. Leitner uses fixed boxes. FSRS estimates two numbers per question, how fast you forget it and how hard it is, and schedules the review when your chance of remembering drops to a target such as 90 %. Confirmed FSRS-6 predicts better than the baseline when repeat reviews on the same day are left out (log loss 0.346 vs 0.395; log loss measures how wrong the predicted chances were, lower is better). When same-day repeats are counted, it scores 0.384 vs 0.382, slightly worse; the benchmark does not explain why. SM-2 is the older method behind classic Anki: one "ease" number per question stretches each gap. A maintained library exists (ts-fsrs, MIT license).

Why it matters

The review screen of the app depends on this choice. Starting with Leitner keeps the first version small. If the review history is kept (chapter 2 leaves where open), you can switch to FSRS later. The 50–300 concepts is an estimate of a year of your learning, not a measured number.

What we don't know

Hypothesis FSRS tunes itself with thousands of reviews; with a few hundred it runs on default settings, and its advantage there is unmeasured.

One more choice shapes every view: how concepts are grouped.

7How do I slice concepts into views?

Short answer No single classification places every concept. The candidate is to tag each concept on three independent axes, called facets: layer, domain and concern. Concepts that span layers stay in one place and connect through relations. This is a hypothesis: the taxonomy sources were not fetched.

Case

HSTS (HTTP Strict Transport Security) is a header the server sends and the browser enforces: "use https for this site from now on". Is it client, network or server? A single tree forces a wrong answer. With facets: layer = network, domain = web, concern = security. Its link to the browser is a relation: "HSTS forces HTTPS".

Mechanism

A facet is one independent way to classify, like filtering a store by size and by color at the same time. Three facets:

  • Layer: the same client / network / server / data used in chapter 4's views.
  • Domain: the kind of product, such as web, mobile, or AI models.
  • Concern: the quality the concept serves, such as security or performance.

Each facet is a field in the concept file's frontmatter. Known classifications each cover only one axis: network layers (the protocol stack, from cables up to HTTP) cover protocols only; C4 levels (system, container, component, code) cover zoom level; quality attributes (an ISO list such as security and reliability) cover concerns.

Why it matters

It defines what a view is: a filter over facets, never a copy of concepts.

What we don't know

Hypothesis The lists inside each facet are examples. Ask Should each concept have exactly one layer?

Glossary

Kill criterion
An answer agreed in advance that would cancel the project, here: an existing tool already meets the four musts.
Layer
Where a concept lives in a system: client, network, server or data.
Probe
A small throwaway program built to measure one thing.
Challenger
A separate AI reviewer with no prior context that checks each claim against its source.
Capture skill
An instruction package for Claude Code that saves a concept during a session.
Concept
One unit of architecture knowledge, such as "__Host- cookie prefix". Stored once.
Relation
A typed, directed link between two concepts, such as "requires" or "complements", with a source.
Effect size
How far a group's average moved compared with another group, measured in units of how spread the scores are.
Markdown
Plain text with light formatting marks; readable in any editor.
Frontmatter
The block at the top of a Markdown file that holds structured fields.
Explain-back
Writing a relation's reason in your own words before saving it.
SEE-I
State, Elaborate, Exemplify, Illustrate: four steps to explain a concept in your own words.
Layered layout
A drawing method that sorts nodes into ranks and reorders them to reduce crossing lines.
Partition
A group the layout must keep together and in order, used here for layers.
Adjacency matrix
A grid with concepts as rows and columns; each cell shows the relation between a pair.
MCP (Model Context Protocol)
The standard Claude Code uses to call outside tools.
stdio
Talking to a child program through its text input and output, without a network port.
Scheduler
The rule that decides when a recall question comes back.
FSRS
Free Spaced Repetition Scheduler: estimates how fast you forget each item and schedules reviews to hit a target memory rate.
Facet
One independent axis of classification, such as layer or domain.
